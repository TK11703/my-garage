**Input**: Design documents from `/specs/007-email-ingestion-api/`

**Prerequisites**: plan.md, spec.md, research.md (R1-R21), data-model.md, contracts/ (`api.openapi.yaml`, `intake-email.example.json`, `web-routes.md`), quickstart.md

**Organization**: Tasks are grouped by user story and follow the structure in plan.md. Story numbers match spec.md: US1 accept a transformed email (P1), US2 match the sender and queue drafts (P1), US3 review, include, or discard (P1), US4 read PDF and image attachments (P2), US5 repeated and retried submissions (P2), US6 email history (P3). US2 and US3 need US1; US4 extends US2; see Dependencies.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks)
- **[Story]**: US1-US6, only on user-story phase tasks
- Constraints from data-model.md and research.md are quoted in the task that creates the artifact; do not loosen them
- No new packages (T002 found that `DefaultAzureCredential` already comes with the existing Azure SDK dependencies; no new projects). New Aspire resources: none (two new containers on the existing `blobs` resource, created at runtime)
- Constitution v1.3.0 "trusted service intake exception": the intake endpoint may find the owner from the sender address; every other endpoint and operation derives the owner from validated claims
- Names (keep identical in every layer): features `EmailIntake`, `Drafts`, `Notifications`, `VehicleDocuments`, `Users`; tables `user_profiles`, `email_submissions`, `email_attachments`, `maintenance_drafts`, `notifications`, `vehicle_documents`; containers `email-intake` and `vehicle-documents`; app role `Email.Ingest`
- Enumerations travel as lowercase snake_case strings in JSON (`DraftKind`: `service_record`, `fuel`, `energy`, `inspection`, `registration`, `insurance`, `tax`; `DraftState`: `needs_review`, `manual_entry`, `included`, `discarded`, `expired`; `VehicleMatch`: `vin`, `description`, `only_vehicle`, `none`) using `JsonStringEnumConverter` with a snake_case naming policy on the enum, and are stored as the same lowercase text; conversion is explicit in the Api mappers (research R11). The enums inside the proposal sections reuse the existing feature 005/006 enums and keep their PascalCase JSON names (`BiAnnual`, `PersonalProperty`)
- Repository method shape (all async, last parameter `CancellationToken cancellationToken`); every owner-specific statement filters `owner_id = @OwnerId` in SQL (draft, attachment, notification tables) or proves ownership with `JOIN vehicles v ON v.id = <table>.vehicle_id WHERE v.owner_id = @OwnerId` (vehicle documents and records)
- Endpoints use `MapGroup(...).WithTags(...)`, `CurrentOwner.Get(user)` with `VehiclesEndpoints.NoOwner()` / `NotFound()`, `ValidationFilter<TRequest>`, `Produces`/`ProducesProblem` for every status, ids from `Guid.CreateVersion7()`, time from `TimeProvider`
- Logs carry ids, counts, statuses, and durations only: never sender addresses, subjects, email text, attachment content, extracted values, or tokens (FR-029)
- Existing insert scripts that the accept transaction reuses (verify names before use): `Scripts/ServiceRecords/Insert.sql`, `InsertLineItem.sql`, `InsertPart.sql`; `Scripts/FuelEnergyEntries/Insert.sql`; `Scripts/Inspections/Insert.sql`; `Scripts/Registrations/Insert.sql`; `Scripts/Insurance/Insert.sql`; `Scripts/Taxes/Insert.sql`

## Dependencies & Execution Order

- **US3 (P1)**: after US2 for end-to-end use, but its repository, endpoint, and Web tasks only need Phase 2 plus hand-inserted drafts (T008), so it can start in parallel with US2 once T035 (shared enums and proposal DTO) exists.

## Implementation Strategy

### MVP first (US1 only)

1. Phase 1 and Phase 2.
2. US1: the workflow can hand over email, the API authenticates it, finds the user, stores everything safely, and answers uniformly. Validate with quickstart steps 1-3 and stop to demonstrate.
3. This alone delivers no user-visible value; the first user-visible increment is US1 + US2 + US3 (the P1 set).

### Incremental delivery

1. US1 -> intake demo. 2. US2 -> drafts and notifications appear (with a fake or real extractor). 3. US3 -> review and accept: the first complete user journey (text-only emails, plus hand-added attachments in tests). 4. US4 -> PDF and image reading. 5. US5 -> retry and duplicate hardening. 6. US6 -> history. 7. Polish and the pull request.

### Notes

- Keep every task's constraints as quoted; do not loosen a check constraint, limit, or status list.
- A kept original is copied before the database commit and the intake copy is deleted after it (research R10); never reverse that order.
- Never add a public blob address, a SAS link, or a different CSS/UI framework; never log email content.
